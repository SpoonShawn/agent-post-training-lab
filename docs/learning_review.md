## 六个需要自己讲清的问题

1. **为什么不能只看工具序列？** 多条合法路径可能完成同一任务。评价目标是状态、公开约束和必要证据，而不是模仿唯一答案。
2. **为什么终态正确还可能失败？** 可能漏了中间动作、没有读取要求的状态，或最终回答与失败记录矛盾。后台真值、模型实际观测、最终声明是三件事。
3. **320条为什么展开成3956个样本？** 每段轨迹有多轮assistant，每轮以此前消息为上下文监督下一轮；历史和工具内容label为-100。这不是3956个独立业务任务。
4. **LoRA到底更新什么？** 本项目训练可训练低秩适配参数33030144，基础权重不按全参方式更新；r16/alpha32、单epoch、495优化步。不要把优化步、工具步、轨迹数混为一谈。
5. **为什么低验证loss不够？** 验证用正确历史预测下一轮，与自主多轮执行不同。模板近似使loss容易很低；新挑战暴露表达和状态条件的脆弱性，但还不能凭此证明经典过拟合。
6. **为什么不能反复改测试集追高分？** 看过结果再改题/规则会影响比较。保留原始分数，新协议单列；用已看过案例开发后，需要新确认数据。

这支持“构建了可复现评估与后训练实验，并通过压力测试定位能力边界”，不支持“真实BugOps部署100%”“通用规划突破”或“解决了过拟合”。可以坦率说明AI辅助实现和审计；个人贡献按实际参与、理解和验证程度描述。

## 用一个失败案例练习

SFT回答：“实际工具失败1次；本轮未发生工具失败。”先看两句逻辑是否一致，再看轨迹是否确有失败；不能因为数字对就忽略整句错误。再对比Base只查空日志的只读题：没有取得HUD状态时说“不知道”不算幻觉，但用户要求读取，模型没完成。两类失败原因不同，修复路径也应不同。
