## Bad case

1. challenge_expression_4400f2f0e416_home_rewrite：step0先query_logs取得[]，之后正确设置low→high→standard并进入battle，最后说“已查询本轮日志”。字面确实调用过日志，但未获得后续操作证据。要求虽有“叙述顺序不代表操作顺序”，模型仍受出现顺序影响。
2. challenge_structure_length1_home_dungeon_select：停在dungeon_select尝试改画质和直接跳settings/graphics，多次无效；没有先back_home，最终无答案。不能用“取证规则过严”解释该真正的操作规划失败。
3. challenge_structure_length5_home_settings：要求standard→low→high→low→standard，实际成功设置只有low→high→low→standard，漏掉第一次standard；终态正确但顺序/次数未满足。模型还把最初在settings设置画质失败说成零失败。本阶段不正式赋予语义复核标签，但保留完整证据。
4. challenge_recovery_navigate_graphics_battle：反复battle→settings非法跳转和inspect，未先back_home，因而未触发预设graphics导航故障。不能归因为模型遇到新故障后不懂重试。

## 遇到的问题与原因分析

已证实：SFT相对Base提升，但表达顺序变化、部分起点和5次动作暴露脆弱性；不能从pilot100%推出可靠泛化。尚不能用单seed、18组合组诊断经典统计意义的过拟合。

构造局限：重排将日志请求前置，混合了指令出现顺序和日志采集时机两因素；虽声明叙述非执行顺序，但“本次日志”采集时机仍可能存在理解边界。保留冻结分数并解释，不把0/20宣传成所有自然语言改写都失败；也不立即改题重跑替换原结果。将来若增加“所有操作完成后再查询日志”的显式对照，应作为新实验版本单独报告。
