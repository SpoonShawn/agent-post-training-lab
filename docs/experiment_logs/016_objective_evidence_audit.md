# 016 — 客观证据审计与后续实验边界

## 状态与证据

2026-09-14记录；既有结果回顾审计完成，无新GPU推理。输入为ec581f4的四份pilot结果，答案审查为阶段015。新增scripts/audit_answer_evidence.py和results/audit/pilot_v1_evidence/四份审计文件；每条输出绑定源文件SHA和case/result SHA。不是评分协议升级。

## 实验目标

将“答案与工具证据矛盾”转为可重现的辅助检查；避免纯人工数错，也避免重新落入关键词自动判整题通过的缺陷。用户希望实验可用于面试，目标是提高证据质量，不是提高表面成绩。

## 配置与数据集

冻结pilot_v1、2.3协议与已保存Base/SFT输出不变。验证及确认各80条×两个模型，共320条；本阶段不限执行通过项。CPU读取轨迹，不加载模型。完整工具返回而非应用日志作为调用失败证据来源。

## 指标

输出工具ok=false数量、工具成功返回但验证success=false数量，二者分开显示并合计为本审计的失败事件数；同时保留末次工具状态观测、记录的终态、完整日志返回及失败返回。该事件口径是审计信息，不替换冻结evaluator的指标定义。

只解析独立分句中的“实际发生的失败次数：N（次）”及“实际工具失败N次”，兼容简单Markdown。其他措辞、范围、引用和否定不作理解承诺，保留待审；多个冲突数字也待审。数字匹配只叫matched_count_only，所有记录semantic_verdict均not_assigned，requires_semantic_review始终true。状态和恢复证据提供给复核者，不用自由文本关键词自动判定完整语义。

## Bad case

阶段015六条Base错报零失败均属明确数字矛盾；完整证据按ID在审计JSONL可查。新增测试反例：答案“实际工具失败0次；所有版本都已修复。”即使数字匹配也必须保留语义待审；“并非实际工具失败0次”和范围/引用不强行解析。

## 遇到的问题与原因分析

1. 应用日志未覆盖全部工具错误，仅数日志可能低估失败；直接提取调用返回。
2. 自然语言规则覆盖不全，贸然拓宽会误解否定/范围；选择低覆盖、明确弃权，不用模板匹配代替通用语义判断。
3. 验证/确认仅4组，320条训练仅16组，数据同质；本轮高分不足以支撑通用能力结论。
4. 检查agent/environment.py确认当前故障按operation/target及剩余times触发，未实现指定第N次才开始失败。不同操作上的首次失败可测试，但不能把“第三次画质设置失败”写成已有功能。

## 解决方案与设计变更

审计脚本与冻结运行代码分离；不修改evaluator、数据、训练或历史复核。输出默认拒绝覆盖，保留文件来源。新增6个测试检查真实调用错误、验证false、否定/范围弃权、矛盾声明、Markdown及数字匹配不自动批准答案。
