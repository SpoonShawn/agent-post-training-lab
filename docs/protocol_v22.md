# Evaluator v2.2：原理与恢复过程约束

## 评估器是什么

当前是“程序规则检查 + 有来源的答案语义复核”，不是另一个模型自动包办打分，也不是用整条参考轨迹做唯一答案。

输入是 case（题目、初始环境、故障计划、成功条件）和 result（实际调用、参数、逐步工具返回、最终环境状态、最终答案）。环境状态来自模拟器，答案中的自述不能替代它。

| 层 | 依据 | 用途 |
|---|---|---|
| 调用诊断 | 解析是否合法、工具是否存在、参数、失败与重复次数 | 定位格式/工具/效率错误，不单独等同任务失败 |
| 执行条件 | 最终环境状态、必须取得的日志/知识证据、实际故障后恢复 | 确认事情是否完成 |
| 过程条件（2.2新增） | 题目显式要求对应的事件顺序 | 确认是否遵守必要步骤，不强制完整唯一路径 |
| 答案复核 | 完整问题、实际证据、最终回答；pass/fail/uncertain及理由 | 检查重要遗漏、矛盾、编造和过度保证 |

2.2执行成功 = 2.1执行条件通过 AND 过程条件通过。

任务通过 = 执行成功 AND 答案pass。执行失败或答案fail则任务失败；执行成功且答案pending/uncertain则任务未决。全体未决清零前不发布最终点估计；不丢弃未决分母。另报类别、长链路、恢复率；工具精确匹配仍是诊断。

答案判定不是新写一个“出现某个词就失败”的规则。知识库提供验证记录即可支持引用验证结论，查询任务不必亲自再做验证；无任何证据却称已验证才是问题。当前复核主要是作者AI自审加5条用户参与裁决，非独立盲审。

## 2.2 修复范围

对两个已审查的恢复任务族 recovery_navigation / recovery_action（60条），导出的case增加显式 process_constraints=["observe_state_before_retry"]。其他300条为空数组。不是评分时从模型答案推断要求。新增未知恢复族必须提供/审查约束，不能静默跳过。

恢复题明确要求失败后检查状态再重试。因此每个识别出的预设故障，必须满足：

故障返回 → 后续模型轮成功读取状态 → 更后模型轮第一次再次尝试同一目标操作。

- 只认故障之后、第一次重试之前的检查；事前检查或事后补查不算。
- 同轮预先批量调用不能证明模型根据新反馈决定重试，因此不同轮次是必要条件。轮次按轨迹数组位置计算，不信任可重复的step显示标签。
- inspect_ui_state的状态，或verify_state返回的current_state均可。即使verify的预期不匹配，只要工具成功返回实际状态，也算观察；不强制唯一工具名。
- 必须有current_page；修改画质时还需graphics_preset。只取得版本、日志、空对象、检查调用报错都不能替代这些状态证据。
- 改变状态的动作不当作只读检查。当前接受工具能力是明确白名单；未来新增只读状态工具需显式扩展并测试。
- 第一次未经检查的重试不能由更晚一次合规重试“洗掉”。
- 过程通过不替代终态、日志或实际恢复成功；过程判断只是新增必要条件。

指标新增process_success、process_violations、process_evidence和execution_success_before_process。证据记录故障/观察/重试轮次及缺失原因。未触发故障或未重试也会失败，不仅检查成功样本。
