# 从一次低分 baseline 到可审计评估：BugOps 实验问题记录

记录日期：2026-09-10。用途：复盘真实实验工作中遇到的问题、定位方法、修复取舍和仍未解决的边界。

这里的“真实”指实际运行模型、读取真实输出、修复实际代码的实验过程。BugOps 的应用状态、工具和故障均为合成模拟，不是生产 Android 应用故障数据。不能将本实验能力结论外推为真实设备自动测试能力。

## 1. 先保留证据，再解释低分

已留存的历史节点：

- `287ffee`：Evaluator v2、360 条 benchmark 及运行支持。
- `c6a8005`：SuperPOD 真实 baseline 输出。
- `0fecffa`：独立的 v2.1 回顾审计入口；当时尚未接入正式推理、汇总入口。
- 本次修复：正式入口协议分流、可追溯答案复核、待审分母保护、补跑输入以及本记录。准确提交号以 Git 历史为准。

原始输出：`results/baseline/qwen3_4b_baseline_v2.jsonl`，360 条；SHA-256 为 `0f7d39563c3b319ed1bf38e43a1108a2288914834c79f2aa22cd7b4bc603601c`。

原 v2 任务成功率为 142/360，约 39.4%。这不是后来要“覆盖掉的错误数字”，而是原协议下可复现的结果。修订后数字必须同时说明协议、分母和复核状态。

### 当时为什么值得怀疑评分器？

工具格式有效率约 99.9%，但导航 0/30、恢复 1/60；知识题参数准确率为 0。组合很反常，但**反常只能触发审计，不能证明模型其实正确**。应回到逐条输入、工具返回、最终状态、回答和每个评分条件。

## 2. 唯一参考路径不等于唯一正确路径

案例：`navigate_graphics_001`。

- 用户目标：从 home 经 settings 进入 graphics，并验证页面。
- 实际调用：`get_build_info → navigate_ui → navigate_ui`。
- 最终状态：graphics、high、非黑屏；答案准确报告这些字段。
- 旧规则：还必须出现指定 `inspect_ui_state` 和 `verify_state` 的返回。
- 问题：导航动作本身已经提供状态，额外指定验证工具把一种实现方式变成唯一通过条件。

修复：对导航／长链路／恢复，移除这两类工具身份的硬约束，保留目标状态与其他必要证据。参考轨迹的工具 precision/recall、exact match 仍保留，但只用于诊断，不能等同任务完成率。

回归测试：正确状态且没有独立 verify 调用应通过执行；最终页面仍为 home 则必须失败。不是删除所有验证要求。

适用边界：本模拟环境的 harness 能可靠报告终态。如果换成真实 GUI、异步系统或可能陈旧的缓存，必须重新定义观测来源、时间和可信度，不能照搬“最后有个正确字段就算完成”。

## 3. 中文同义与否定会击穿关键词打分

案例 A：`return_home_then_dungeon_002`。

回答写“出现黑屏”“属于缺陷复现”，旧白名单接受“出现了黑屏”等固定表达。模型表达正确，不代表所有其他要求也正确，但仅凭缺一个“了”拒绝回答是明显的测量问题。

案例 B：`negative_control_ios_002`。

回答写“未出现黑屏或加载失败等异常现象”。旧 forbidden_any 包含“加载失败”，忽略了否定作用域。它会把“没有发生 X”当成“发生 X”。

案例 C：`workaround_black_screen_007`。

回答写“规避方案生效”，未命中“规避成功／正常加载”等有限白名单。

修复：不再用这些关键词决定 v2.1 最终回答真值，改为显式 pass/fail/uncertain 复核，核对问题和工具证据。执行层仍可程序判定。

重要反例：B 和 C 的轨迹还缺少当前协议要求的日志。修掉语言误判不等于整条任务通过。“规避已验证”和“已复现故障”措辞也可能混淆，应由复核指出，不通过新增宽泛关键词掩盖。

经验：不能不断把已看到的答案加进白名单。应测试同义替换、否定、无关段落包含关键词、答非所问、错误事实但关键词齐全等正反例。自然语言复核也会有偏差，需要署名、理由和争议复审，而不是把人工或 LLM 判断称为绝对真值。

## 4. 搜索 query 不应与结构化参数采用同一种精确匹配

知识类工具可用不同关键词获得同一个事件记录。旧参数指标将整段检索文本与参考字符串比较，因此出现“工具选择几乎正确，但参数全错”的反常结果。

修复：新增 `structured_argument_accuracy`，排除 `search_knowledge` 的自由文本。检索是否有效继续看返回证据；旧 `argument_accuracy` 留作历史诊断，不把两个口径混为一个。

边界：拿到正确事件编号也不等于答案正确。返回结果可能过宽、包含冲突记录，模型也可能总结错误。当前证据包含检查不是完整检索质量指标。

## 5. 题目漏信息，不能要求模型猜隐藏标签

案例：`knowledge_black_screen_011` 的原问题是“请查询知识库，用事件编号查询黑屏根因字段。”没有提供编号。

实际答案恰好查询到 INC-101，也不能证明输入设计合理。共 8 条类似问题补入事件编号。

修复边界：输入变了就必须重新推理，不能把旧输出接到新问题后评分。旧输出一律排除，包括原先答对的，避免只排除失败样本造成选择偏差。

工程措施：生成单独 `rerun_v21.jsonl`；正式 v2.1 scorer 校验 result.query 与 case.query 一致；协议、模型、代码和输入指纹均留档。这个校验能发现直接错配，但不是密码学证明推理过程真实，仍需保留原始运行产物。

## 6. 恢复测试需要验证“失败后恢复”，不是只看终态

案例：`recovery_navigation_001`。

实际轨迹经历首次导航故障、检查 home、下一轮重试成功、进入 graphics。旧规则因未调用独立 verify 工具拒绝。

修订后的恢复执行仍要求实际观察到预设故障，并在后续模型轮次成功恢复。未触发故障、同一轮排列多个调用或只看最终状态，不能替代反馈驱动恢复。

结果：恢复执行成功 40/60，明显高于旧任务成功 1/60。但前者未包含回答复核，不能写成“恢复任务成功率从 1.7% 提升到 66.7%”。这是同一模型轨迹在不同测量条件下的诊断，不是训练收益。

## 7. 仍然有真实的长链路能力问题

案例：`reproduce_black_screen_001`。

- 任务要求 Android 2.3.1 high 下启动多人副本，复现黑屏并获取日志。
- 模型尝试不合时宜地改标准画质，还在错误页面执行动作。
- 最终停在 multiplayer_dungeon，而不是触发战斗的 battle；没有完成关键启动，也没有所需日志。
- 回答却把未完成的操作解释成“未复现”，甚至建议用标准画质验证缺陷存在，与原复现条件相悖。

这不能靠放宽 evaluator 修好。需要优化前置条件理解、状态跟踪、执行规划、失败反馈利用和证据约束。后训练时可以围绕这些错误类型设计独立训练任务，但不能把这条 eval 直接改写进训练集。

修订后长链路执行只有 3/120。因此“低分全部是评分器的问题”同样不成立。与此同时，当前协议中部分日志要求未在问题里明确表达，这也是后续题目审查要查的残余风险；本轮保留已有证据条件并公开边界，没有为了提高分数继续删除。

## 8. 新引入的 null 会让汇总悄悄变错

分离执行和回答后，成功执行但未审答案是 `task_success=null`；执行失败是 false。

旧汇总通用做法是丢弃 null 后求平均。例如 1 条失败、1 条待审，就会输出 0/1=0%，看起来像完整测试成绩。若仅先复核容易成功的答案，又会出现反向偏高。

修复：明确通过、失败、未决的数量。只要该组存在未决，就不发布完整任务率；另外输出 `通过数/总数` 至 `(通过数+未决数)/总数` 的逻辑边界。整体、类别、难度、场景族和类别宏平均都要保护。

这不是置信区间，也不是模型能力的估计区间，只说明“待审判定不同会让这个固定集合的最终成绩落在哪”。工具调用级执行成功率与任务级执行达成率也分别命名，避免看见同一个 success 就混用。

## 9. 有审计脚本，不等于正式入口已经修好

`0fecffa` 阶段只有独立审计入口。若把修订输入交给旧 runner 或用旧 summarizer 重算，会再次使用旧评分逻辑，造成文件叫 v21、实际上算 v2 的错觉。

本轮增加 `evaluation/scoring.py` 统一分流；runner 写入对应协议版本；汇总校验协议并按版本评分；运行指纹包括新评分代码；未知或混合版本拒绝执行／汇总。

回归测试不仅调用内部函数，还覆盖 metadata 构建、JSONL 加载、汇总 CLI 和队列导出。历史 v2 仍走原逻辑，不能只验证新版本然后破坏历史可复现性。

## 10. 复核文件也是实验数据，需要防错配

危险场景：同一个 case ID 重新跑过模型，但把上次 pass 复用到新的错误答案；或者把作者自审说成独立人工评审。

修复：复核绑定源文件 SHA-256 和逐条 case/result SHA-256，记录版本、审阅者类型、时间、判定和理由。导入拒绝未知／重复 ID、过期证据、空署名和 pending 模板。

队列提供实际工具返回，不要求审阅者只看回答自述。队列不展示旧分数、模型名称，但来源哈希并不会保证真正盲审，署名字段也不会自动证明审阅身份。独立性只能如实陈述。

当前没有伪造已完成的复核。206 条仍待审；代码支持导入不代表已经完成语义审查。

## 11. 路径、GPU 调度与断点续跑也是实验的一部分

此前给操作指令时没有先进入实验目录，也没有先申请 GPU，这是操作指导缺陷。后果可能是找不到脚本、运行错误版本，或误在共享登录节点启动推理。

修复后的指令严格分为：登录节点更新及 CPU 审计 → 申请 GPU → 计算节点重新进入目录并激活环境 → 检查 GPU → 推理 → 退出释放资源 → 登录节点汇总。

已有实验结果不允许默认覆盖；新实验使用新输出路径。代码变化导致指纹不同而拒绝 resume 是保护机制，不应手动改哈希绕过。旧 352 条重评分和新 8 条推理来源不同，也不能简单拼接后当作同一原始运行。

完整可复制命令见 [protocol_v21.md](protocol_v21.md)。本地测试不需要加载模型；SuperPOD 推理仍需要真实资源分配。

尚需：完成答案复核；在 GPU 上补跑 8 条或完整重跑；独立审查题目要求与隐藏条件是否一致；构造未参与协议开发的确认集；冻结后再比较 Base/SFT。当前 benchmark 已用于协议开发，应标为开发／审计集。

## 13. 如何判断是在修 bug，还是在迎合结果？

每次修订先回答：

1. 能否给出不依赖模型名字、分数高低的规则理由？
2. 能否构造修复前被误判的正例，以及修复后仍须拒绝的反例？
3. 是否对所有模型、所有同类样本一致应用，而不是只修失败 case？
4. 是否保留原始输入、输出、协议与变更记录？
5. 输入变化是否重新推理，标准变化是否所有比较模型统一重算？
6. 是否承认这套已看过的数据不再是独立确认依据？

这些条件比“修改了几次 evaluator”更重要。真实实验允许修测量缺陷，但不能把修改测量工具包装成模型进步。
